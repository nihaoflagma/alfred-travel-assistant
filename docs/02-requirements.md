# 2. Требования и правила

## Функциональные требования

| ID | Требование | Критерий |
|---|---|---|
| FR-01 | Мониторить экземпляр рейса по перевозчику, номеру, дате вылета и аэропортам | Одноимённые рейсы разных дат не смешиваются |
| FR-02 | Получать webhook/API; рассылки использовать как дополнительный источник | Каждое событие содержит источник и времена source_updated_at, received_at |
| FR-03 | Отсекать дубликаты и устаревшие обновления | Старое событие сохраняется в аудите без изменения текущего состояния |
| FR-04 | Выявлять задержку, отмену и конфликты зависимых событий | В плане указана причина конфликта и затронутые элементы |
| FR-05 | Уведомлять затронутых участников | Запись доступна в центре уведомлений независимо от push |
| FR-06 | Искать альтернативы для всех пассажиров затронутого бронирования | Для каждого варианта видны цена, места, багаж, пересадки и визовая проверка |
| FR-07 | Предлагать активности на время ожидания | Учитываются место, время, часы работы, дорога и ограничения выхода из транзитной зоны |
| FR-08 | Согласовывать замену и обновлять общий план | Проверены права, версия, цена, срок предложения и результат поставщика |
| FR-09 | Синхронизировать офлайн-клиента | После подключения клиент получает актуальную версию плана и непрочитанные уведомления |
| FR-10 | Ограничивать хранение паспортов | Просроченный документ удалён из активного хранилища; фиксируется обезличенный факт удаления |

## Бизнес-правила

BR-01. Сравнения и длительности считаются по абсолютным моментам UTC. В интерфейсе показываются локальное время, дата и зона IANA соответствующего аэропорта. Переход через полночь и смена сезонного смещения не должны менять фактическую длительность.

BR-02. Новый факт о времени рейса обновляет фактическую часть плана автоматически. Отель, активность или трансфер помечаются как конфликтные; сервис не заявляет, что поставщик перенёс бронь, пока не получено подтверждение.

BR-03. Отмена рейса не означает автоматический возврат денег и не удаляет старую бронь. Замена хранится со ссылкой на исходную, денежные операции учитываются отдельно.

BR-04. Альтернатива проверяется для каждого пассажира. Нехватка мест или невыполнимое требование хотя бы одного пассажира делает общий вариант недоступным. Разделение группы требует отдельного согласования и в MVP не поддерживается.

BR-05. Визовая проверка имеет результат PASS, FAIL или UNKNOWN. FAIL исключается; UNKNOWN отображается только как вариант, требующий проверки, и блокирует автоматическое подтверждение. Паспортные номера для ранжирования не нужны.

BR-06. Любое существенное изменение цены, состава рейсов или багажа после повторной проверки требует нового подтверждения. Платёжные реквизиты обрабатывает платёжный провайдер; сервис хранит ссылку/токен и статус.

BR-07. Предложение связано с версией плана и expires_at. Просроченное предложение или изменившийся план требуют повторного поиска. Если конкурентное событие изменило план во время бронирования, уже купленный билет сохраняется, а итоговая синхронизация переводится на сверку; факт покупки нельзя потерять.

BR-08. Повторное подтверждение с тем же ключом идемпотентности возвращает ту же операцию. Тот же ключ с другим телом запроса даёт конфликт. Параллельно допускается одна активная операция замены одного бронирования.

## Предлагаемые требования к качеству

Это цели для согласования и нагрузочных проверок, а не измеренные свойства готового продукта.

| ID | Цель | Как проверять |
|---|---|---|
| NFR-01 | p95 обработки принятого валидного события до записи в план ≤ 10 с | Метрика received_at → plan_committed_at; без времени недоступности провайдера |
| NFR-02 | p95 постановки уведомления в отправку ≤ 30 с после изменения | Outbox → очередь отправки; доставка внешним каналом отдельно |
| NFR-03 | Доступность чтения плана 99,5% в месяц | Доля успешных запросов, включая период отказа источника статусов |
| NFR-04 | Повторы не создают повторную покупку и одинаковое уведомление | Проверка уникальных ключей события, операции и получателя |
| NFR-05 | Доступ к персональным данным по ролям и поездке | Негативные проверки прав; отсутствие паспортов в логах и событиях |

Для согласования нагрузки: число поездок, рейсов в мониторинге, максимальный поток событий, количество участников и лимиты внешних API.
