# 1. Условие и границы решения

## Исходное задание

Спроектировать часть сервиса планирования путешествий, которая отслеживает рейсы через внешние API или рассылки, уведомляет о задержках и отменах, предлагает альтернативные рейсы или активности и обновляет общий план поездки. Необходимо учитывать задержку поступления данных, офлайн-пользователей, багаж, визы и часовые пояса. Паспортные данные нельзя хранить дольше, чем требуется для поездки.

Источник требований — два предоставленных скриншота задания. Следующие решения и численные параметры являются предложением автора решения, а не дополнительными фактами из условия.

## Цель и пользователи

Цель — сократить ручные действия при нарушении расписания и сохранить согласованность маршрута. Путешественник получает объяснение изменения и варианты действий. Организатор групповой поездки согласует общий маршрут. Сотрудник поддержки разбирает неопределённый результат внешней операции, имея ограниченный доступ и журнал действий.

## MVP

В MVP входят мониторинг добавленных рейсов, обнаружение изменений и конфликтов, центр уведомлений и push/email, подбор альтернативных рейсов и активностей, подтверждение изменения организатором и общий план с версиями. Поиск ведётся через одного согласованного поставщика статусов и одного агрегатора предложений; интерфейсы выделены так, чтобы добавлять провайдеров позднее.

Покупка альтернативного рейса входит в проектируемый сценарий только при наличии соответствующего API поставщика. Если доступен лишь поиск, пользователь переходит к поставщику, а сервис импортирует подтверждённое бронирование. В репозитории описан контракт внутренней операции, а не готовая интеграция с конкретной авиакомпанией.

Исходный сервис также может искать отели, трансферы и собирать отзывы. Разработка всех этих подсистем вне данного кейса: используются существующие бронирования и события плана. Перенос платных услуг не выполняется без подтверждения.

## Полномочия

| Роль | Возможности |
|---|---|
| Организатор | Приглашать участников; подтверждать изменения общей поездки в пределах выданных полномочий |
| Участник | Читать общий план; задавать собственные ограничения; читать свои уведомления |
| Поддержка | Читать технический аудит и инициировать сверку неопределённой операции; доступ к паспортам отдельно ограничен |

Все API проверяют членство в поездке. Организатор не получает автоматически доступ к документам других участников. Разрешение купить билет для другого человека и согласованный бюджет фиксируются отдельно; при отсутствии полномочий изменение не запускается.

## Допущения и вопросы заказчику

| Тема | Принятое решение | Что уточнить перед разработкой |
|---|---|---|
| Значимая задержка | От 15 минут либо любое изменение, создающее конфликт; отмена всегда значима | Порог для разных типов поездок |
| Подтверждение | Общий план меняет организатор с полномочиями | Нужно ли голосование участников |
| Каналы | Push и email; SMS возможен позднее | Стоимость, согласия и доступные каналы |
| Визы | Проверка по актуальному источнику правил; UNKNOWN требует проверки | Поставщик и покрытие стран |
| Бронирование | Предварительная цена не гарантирована; повторная проверка перед действием | Возможность обмена, возврата и резервирования мест |
| Паспорт | Удаление по завершении потребности, предельный срок определяется политикой поездки | Точный срок и допустимые исключения хранения |

Термин «альтернатива» означает предложение. Даже подходящий вариант не гарантирует посадку, доступность мест или юридическую допустимость транзита без подтверждения соответствующих поставщиков.
